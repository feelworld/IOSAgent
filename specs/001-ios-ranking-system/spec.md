# Feature Specification: iOS App Ranking System

**Feature Branch**: `001-ios-ranking-system`
**Created**: 2026-03-07
**Status**: Draft
**Input**: User description: "iOS 刷榜系统，分为服务端、客户端和后台。后台负责管理所有客户端的配置和刷榜脚本发布，分为手动管理和智能管理。智能管理根据所有客户端手机信息自动配置脚本策略。服务端控制所有客户端，传达指令和脚本。客户端安装在 iOS 手机上，执行服务端命令，回报结果和手机状态。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 后台手动管理设备并下发脚本 (Priority: P1)

管理员通过后台 Web 界面登录系统，查看所有已注册的 iOS 设备列表及其在线状态。管理员选择一台或多台设备，手动选择一个已发布的刷榜脚本，配置脚本参数（目标 App 名称、操作类型等），然后下发执行命令。设备执行完成后，管理员在后台查看执行结果（成功/失败/异常详情）。

**Why this priority**: 这是系统最基础的能力——人工操控设备执行脚本。没有这个能力，系统无法产生任何价值。手动管理也是验证整个链路（后台→服务端→客户端→回报）是否通畅的基础。

**Independent Test**: 可以通过在后台选择一台在线设备、下发一个简单脚本（如打开 App Store 搜索指定 App）、观察设备执行并查看回报结果来完整测试。

**Acceptance Scenarios**:

1. **Given** 管理员已登录后台且有至少一台在线设备, **When** 选择设备并下发一个刷榜脚本, **Then** 设备收到命令并开始执行，后台显示任务状态为"执行中"
2. **Given** 设备正在执行脚本, **When** 脚本执行完成, **Then** 后台收到执行结果，显示成功/失败状态及详细日志
3. **Given** 管理员选择了多台设备, **When** 批量下发同一脚本, **Then** 所有选中设备均收到命令，各自独立执行并回报结果
4. **Given** 目标设备离线, **When** 管理员尝试下发命令, **Then** 系统提示设备不可用，命令不会发送

---

### User Story 2 - 客户端设备注册与状态上报 (Priority: P1)

iOS 客户端程序安装到越狱设备后首次启动，自动向服务端注册设备信息（设备型号、系统版本、唯一标识等）。注册成功后，客户端定期向服务端发送心跳包，上报当前设备状态（电量、网络状况、App Store 登录状态、当前是否在执行任务等）。服务端收到信息后同步到后台供管理员查看。

**Why this priority**: 设备注册和状态上报是整个系统运作的前提。没有设备注册，后台看不到设备；没有状态上报，无法判断设备是否可用。

**Independent Test**: 在一台越狱 iPhone 上安装客户端，观察服务端是否收到注册请求，后台设备列表是否出现该设备，以及心跳状态是否持续更新。

**Acceptance Scenarios**:

1. **Given** 一台新设备安装了客户端, **When** 客户端首次启动, **Then** 设备信息自动注册到服务端，后台设备列表中出现该设备
2. **Given** 设备已注册, **When** 设备持续运行, **Then** 服务端每隔配置的间隔收到心跳包，后台显示设备为"在线"状态
3. **Given** 设备正常运行, **When** 设备断网超过心跳超时时间, **Then** 服务端将设备标记为"离线"，后台状态同步更新
4. **Given** 设备已注册, **When** 设备上报状态信息, **Then** 后台能查看该设备的电量、网络、App Store 登录状态等详细信息

---

### User Story 3 - 客户端执行远端脚本 (Priority: P1)

客户端接收到服务端下发的脚本命令后，通过 Appium + WebDriverAgent 控制 iOS 设备执行自动化操作（如打开 App Store、搜索目标 App、浏览、下载等）。执行过程中，客户端实时上报执行进度；执行完成后，上报最终结果（成功/失败/错误信息/截图等）。

**Why this priority**: 脚本执行是系统的核心交付能力。设备管理和指令下发最终都是为了让设备执行脚本。

**Independent Test**: 服务端向一台在线设备下发一个"打开 App Store 并搜索指定关键词"的脚本，观察设备是否正确执行操作，服务端是否收到执行结果。

**Acceptance Scenarios**:

1. **Given** 客户端在线且空闲, **When** 收到服务端下发的脚本命令, **Then** 客户端通过 Appium+WDA 执行指定操作
2. **Given** 脚本正在执行, **When** 执行过程中发生错误（如 App Store 未登录）, **Then** 客户端捕获错误并上报错误详情，标记任务失败
3. **Given** 脚本正在执行, **When** 执行时间超过配置的超时时间, **Then** 客户端强制终止脚本并上报超时信息
4. **Given** 脚本执行完成, **When** 结果回传到服务端, **Then** 服务端记录执行结果并同步到后台

---

### User Story 4 - 刷榜脚本管理与发布 (Priority: P2)

管理员在后台创建、编辑和管理刷榜脚本。每个脚本定义一系列自动化操作步骤（如搜索关键词→浏览结果→点击目标 App→下载）。脚本支持版本管理，管理员可以发布新版本或回滚到旧版本。发布后的脚本可供手动管理或智能管理使用。

**Why this priority**: 脚本管理是手动管理和智能管理的基础设施。必须先有脚本管理能力，才能实现后续的策略调度。

**Independent Test**: 在后台创建一个新脚本，编辑其操作步骤，发布为 v1.0，然后修改并发布 v1.1，再回滚到 v1.0，验证版本管理功能正常。

**Acceptance Scenarios**:

1. **Given** 管理员在后台, **When** 通过表单式编辑器创建一个新的刷榜脚本并定义 JSON 结构化操作步骤, **Then** 脚本保存成功并出现在脚本列表中
2. **Given** 一个已有脚本, **When** 管理员修改并发布新版本, **Then** 新版本可用于下发，旧版本保留在版本历史中
3. **Given** 一个有多个版本的脚本, **When** 管理员选择回滚到指定版本, **Then** 该版本成为当前生效版本

---

### User Story 5 - 智能管理：探索阶段（随机策略发现） (Priority: P2)

系统进入智能管理的探索阶段时，自动根据可用设备的手机信息（型号、系统版本、Apple ID 状态等），向不同设备分配不同的脚本策略组合进行随机测试。每次执行后记录操作类型、设备信息和执行效果。经过一段时间的探索后，系统自动分析哪些策略组合产生了有效的刷榜效果。

**Why this priority**: 智能管理是系统的核心差异化能力，探索阶段是智能管理的第一步。但它依赖于手动管理（US1）和脚本执行（US3）能力已就绪。

**Independent Test**: 配置智能管理进入探索模式，分配 5 台设备，观察系统是否自动分配不同策略、记录执行结果、并在一轮探索后产出策略效果分析报告。

**Acceptance Scenarios**:

1. **Given** 管理员在后台配置了参与设备数和探索轮次, **When** 点击"开始探索"触发探索阶段, **Then** 系统自动向选定设备分配不同的脚本策略组合
2. **Given** 探索任务正在执行, **When** 每个设备完成一轮操作, **Then** 系统记录该设备的策略、操作详情和效果指标
3. **Given** 一轮探索完成, **When** 所有设备回报结果, **Then** 系统生成策略效果对比分析，标记有效和无效的策略

---

### User Story 6 - 智能管理：实施阶段（批量执行有效策略） (Priority: P3)

在探索阶段识别出有效的刷榜策略后，管理员确认或系统自动将有效策略批量推送到所有可用设备。系统根据设备特征（型号、状态等）智能分配最适合的策略，统一调度执行。执行过程中持续监控效果，如果某策略效果下降，自动调整或通知管理员。

**Why this priority**: 这是智能管理的最终目标——将有效策略规模化执行。但它依赖探索阶段（US5）先找到有效策略。

**Independent Test**: 从探索阶段的分析结果中选择一个有效策略，配置为实施模式，分配给 10 台设备执行，观察是否全部成功执行并持续监控效果。

**Acceptance Scenarios**:

1. **Given** 探索阶段已产出有效策略, **When** 管理员确认进入实施阶段, **Then** 系统将有效策略分配到所有可用设备
2. **Given** 实施阶段正在运行, **When** 系统检测到某策略效果下降, **Then** 自动调整策略或向管理员发出告警
3. **Given** 大量设备在同时执行, **When** 管理员查看后台仪表盘, **Then** 能看到整体执行进度、成功率、异常设备列表等聚合信息

---

### Edge Cases

- 客户端执行脚本时 App Store 要求输入密码或验证码，如何处理？
  - **假设**：客户端检测到此类弹窗后上报"需要人工干预"状态，服务端暂停该设备的任务
- 同一台设备收到多条命令时如何排队？
  - **假设**：服务端为每台设备维护命令队列，按先入先出顺序执行
- 网络恢复后，离线期间积压的命令如何处理？
  - **假设**：设备重连后从服务端拉取未执行的命令队列，过期命令自动丢弃
- 脚本执行到一半时设备重启怎么办？
  - **假设**：客户端启动后检查是否有未完成任务，上报中断状态，由服务端决定是否重新下发
- Apple 更新 App Store 界面导致脚本失效？
  - **假设**：通过脚本版本管理快速发布修复版本，智能管理自动检测到效果下降后暂停相关策略

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持后台管理员通过 Web 界面查看所有已注册设备的列表和实时状态
- **FR-021**: 系统 MUST 初期提供单一管理员角色，同时在用户和权限模型中预留角色扩展能力（支持未来新增角色并配置对应权限）
- **FR-002**: 系统 MUST 支持客户端自动注册设备信息并定期上报设备状态（心跳机制）
- **FR-003**: 系统 MUST 支持管理员手动选择设备并下发指定刷榜脚本
- **FR-004**: 系统 MUST 支持批量向多台设备同时下发脚本命令
- **FR-005**: 客户端 MUST 通过 Appium + WebDriverAgent 执行自动化操作脚本
- **FR-006**: 客户端 MUST 在脚本执行完成后向服务端回报执行结果（成功/失败/异常详情）
- **FR-007**: 系统 MUST 支持脚本的创建、编辑、版本管理和发布
- **FR-008**: 系统 MUST 支持脚本版本回滚功能
- **FR-009**: 系统 MUST 支持管理员手动触发智能管理探索阶段（配置参与设备数和探索轮次），自动分配不同策略组合到选定设备进行测试
- **FR-010**: 系统 MUST 在探索阶段结束后基于目标 App 下载量增量自动分析策略效果，识别有效策略
- **FR-011**: 系统 MUST 支持智能管理的实施阶段——将有效策略批量推送到所有可用设备
- **FR-012**: 系统 MUST 支持按设备/设备组/全局三个维度管理配置
- **FR-013**: 客户端 MUST 支持脚本超时自动终止机制
- **FR-014**: 系统 MUST 在设备心跳超时后将其标记为离线
- **FR-015**: 系统 MUST 对服务端与客户端之间的通信进行加密
- **FR-016**: 系统 MUST 加密存储 Apple ID 等敏感凭据，禁止明文传输或记录在日志中
- **FR-019**: 系统 MUST 支持为每台设备配置主 Apple ID 和备用 Apple ID 池
- **FR-020**: 系统 MUST 在检测到 Apple ID 封禁或异常时自动切换到备用 Apple ID
- **FR-017**: 系统 MUST 支持客户端断连后自动重连并恢复任务状态
- **FR-018**: 后台 MUST 提供实时仪表盘，展示设备总数、在线率、任务执行进度和成功率等聚合数据

### Key Entities

- **Device（设备）**: 代表一台已注册的 iOS 手机。关键属性：设备唯一标识、型号、系统版本、在线状态、电量、网络状况、当前 Apple ID、所属设备组
- **AppleAccount（Apple ID 账号）**: 代表一个 Apple ID 凭据。关键属性：账号标识、邮箱、状态（正常/封禁/异常）、当前绑定设备、是否为主账号或备用账号
- **Script（脚本）**: 代表一个可执行的刷榜自动化操作流程。关键属性：脚本名称、JSON 结构化操作步骤（每步包含 action/target/params）、当前版本、版本历史、适用条件
- **Task（任务）**: 代表一次脚本下发和执行记录。关键属性：关联设备、关联脚本版本、下发时间、执行状态（待执行/执行中/成功/失败/超时）、执行结果详情
- **Strategy（策略）**: 代表智能管理中的一种脚本+参数组合方案。关键属性：关联脚本、参数配置、适用设备条件、效果评分（基于目标 App 下载量增量）、来源阶段（探索/实施）
- **DeviceGroup（设备组）**: 代表一组设备的逻辑分组。关键属性：组名、包含的设备列表、组级配置
- **User（用户）**: 代表后台系统用户。关键属性：用户名、密码（加密）、角色（初期仅管理员）、权限列表（预留扩展）
- **Role（角色）**: 代表权限角色定义。关键属性：角色名、权限集合（预留，初期仅有管理员角色拥有全部权限）
- **ScriptVersion（脚本版本）**: 代表脚本的一个具体版本快照。关键属性：所属脚本、版本号、JSON 操作步骤、变更说明、发布时间
- **CompanionMachine（伴生机）**: 代表一台管理 iOS 设备的伴生机。关键属性：唯一标识、IP 地址、在线状态、管理的设备列表、最大管理设备数
- **Configuration（配置）**: 代表系统运行参数。关键属性：心跳间隔、脚本超时时间、重试次数、作用范围（设备/设备组/全局）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员从登录后台到成功下发一条脚本命令的操作时间不超过 2 分钟
- **SC-002**: 系统同时管理和调度至少 100 台设备时运行稳定，REST API 响应时间 p95 < 500ms，WebSocket 消息延迟 < 200ms
- **SC-003**: 设备上线到出现在后台设备列表的延迟不超过 10 秒
- **SC-004**: 脚本执行结果从客户端完成到后台可见的延迟不超过 5 秒
- **SC-005**: 智能管理探索阶段在 50 次策略测试后能产出有效策略对比分析
- **SC-006**: 设备断连恢复后 30 秒内自动重新上线并可接收新命令
- **SC-007**: 系统整体可用性达到 99%（按月计算）
- **SC-008**: 批量下发命令到 100 台设备的耗时不超过 30 秒

## Clarifications

### Session 2026-03-07

- Q: 智能管理中"有效策略"的衡量标准是什么？ → A: 以目标 App 的下载量变化（下载次数增量）作为策略有效性的主要衡量指标
- Q: 刷榜脚本的定义格式是什么？ → A: JSON 结构化步骤（每步定义 action/target/params），后台提供表单式编辑器
- Q: Apple ID 与设备的对应关系？ → A: 一对多（每台设备有一个主 Apple ID + 备用 Apple ID 池，封号后自动切换）
- Q: 后台用户角色权限如何设计？ → A: 初期单角色（管理员），但架构预留角色权限扩展能力，日后可新增角色并配置对应权限
- Q: 智能管理探索阶段如何触发？ → A: 管理员手动触发，配置参与设备数和探索轮次后启动

## Assumptions

- 所有 iOS 设备均已越狱，具备安装自定义客户端和运行 Appium + WebDriverAgent 的条件
- 每台设备上已预装 WebDriverAgent 并正确配置
- 设备通过 Wi-Fi 连接到与服务端可通信的网络环境
- Apple ID 已预先在设备上登录 App Store
- 管理员具备基本的脚本配置能力，了解刷榜操作流程
- 系统初期以手动管理为主，智能管理功能逐步迭代完善
- 此处"客户端"指运行在伴生机（Companion Machine，Mac/Linux）上的 Python Agent，而非 iOS 设备上的原生应用。iOS 设备仅运行 WDA（WebDriverAgent），由伴生机通过 HTTP 控制
